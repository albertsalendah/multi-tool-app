# What this project is

A modular automation platform (`README.md`, `docs/architecture/ARCHITECTURE.md`).
Core idea: a Kernel orchestrates, Tools do the work, everything runs
through a Job Manager, and multiple thin clients (web UI, REST API,
CLI) talk to the same running server. One real tool exists today
(`video_downloader` + `video_downloader_interactive`), but the tool
itself is explicitly *not* the point - the platform underneath it is.

# Current state: what's actually built and working

Everything below is implemented, tested, and pushed to `main`:

- **Application Kernel** (`app/kernel.py`) - bootstraps everything,
  owns `run_tool()` (the single entrypoint for executing a tool,
  foreground or background).
- **Tool Registry + Plugin Discovery** (`app/tool_registry.py`) -
  scans `tools/*/manifest.json`, one tool per top-level directory. A
  broken plugin is logged and skipped, not fatal to the others.
- **Job Manager** (`app/job_manager.py`) - `ThreadPoolExecutor`-backed
  background execution, cooperative cancellation.
- **Browser Manager** (`app/browser_manager.py`) - SeleniumBase-based
  (not Playwright - see "Key Decisions" below).
  `acquire()`/`release()`/`shutdown()`, plus a PID-tracking watchdog
  (`acquire(timeout=...)` force-kills a session's real OS browser
  process if not released in time - added this session, see below).
- **Event Bus, Execution Context, Cancellation Token, Scheduler,
  Service Container, Config, Logger** - all built, all tested.
- **Workflow Engine** (`app/workflow.py`, `app/workflow_engine.py`) -
  linear steps (retry/timeout/condition/continue_on_error),
  `ParallelGroup` (concurrent branches, run-to-completion + aggregated
  failures), and `workflow.*` events.
- **Plugin SDK** (`tools/base_tool.py`) - real per-execution
  `initialize() -> validate() -> run() -> cleanup()` lifecycle.
- **REST API** (`app/api.py`, mounted in `main.py`) - `/api/v1`:
  `GET /health`, `GET /tools`, `POST /jobs`, `GET /jobs/{id}`,
  `DELETE /jobs/{id}`, `POST /tools/{name}/run` (sync execution for
  fast tools, refuses anything needing the `browser` capability).
- **CLI** (`cli/`) - installable (`pip install -e .`) `multitool`
  console script, a pure REST API client (talks to a running server
  over HTTP, does not embed the Kernel - this was a deliberate choice,
  see "Key Decisions").
- **Web UI** (`static/`) - fully reconciled with the REST API. Both
  the fast path (`video_downloader`) and the interactive/CAPTCHA path
  (`video_downloader_interactive`) go through the Kernel now; nothing
  bypasses it anymore.
- **`libraries/captcha_manager`** - a shared library (not a registered
  platform service - see `docs/implementation/CAPTCHA_MANAGER.md`),
  actually exercised now by `video_downloader_interactive`.

Run the tests: `python3 -m pytest tests/ -q` from the repo root.
119 pass, 1 pre-existing unrelated failure (see Known Issues).

# Key decisions made this session (with reasoning - don't redo these)

1. **REST API is the platform's primary client interface; CLI and web
   UI are both thin clients over it.** Not an in-process kernel driver
   for the CLI. Reasoning: the whole app already assumes a long-running
   server model (job persistence, shared job history, browser sessions
   living independently of any one client). An in-process CLI would
   duplicate kernel bootstrapping and need the full dependency stack
   (Playwright/SeleniumBase/yt-dlp) just to run a command.

2. **SeleniumBase, not Playwright**, for browser automation. Reasoning:
   `libraries/captcha_manager` was *already* built assuming
   SeleniumBase's API (`sb.cdp.*`, `sb.solve_captcha()`) - aligning
   with existing work instead of fighting it. `BrowserManager` was
   rewritten from Playwright's Browser/BrowserContext model to
   `acquire()`/`release()`/`shutdown()` session semantics, since
   SeleniumBase's `SB()` is a per-session context manager, not a
   shared process you spin cheap sub-contexts from.

3. **Desktop UI and mobile app are deferred**, not cancelled. The
   person's reasoning: get the web app solid first; both would be thin
   `/api/v1` clients anyway, same as the CLI, so nothing about them is
   blocked by this order - it's a priority call.

4. **video_downloader/CAPTCHA-specific improvements are deliberately
   deferred** until "everything else" (the platform itself) is solid.
   This includes: wiring the new BrowserManager timeout into
   `video_downloader_interactive`, and fixing `captcha_manager.py`'s
   120-second-flat manual-wait. Don't start on these unless explicitly
   asked - the person has been consistent about this boundary across
   the whole session.

5. **Per-execution tool state goes on `context` (via
   `context.set_state()`/`get_state()`), never on `self`.**
   `ToolRegistry` keeps ONE shared instance of each tool class across
   every execution, forever - storing state on `self` would race if
   two executions of the same tool ran concurrently (`JobManager`'s
   pool defaults to 4 workers). This bit `video_downloader_interactive`
   specifically (it holds a live browser session per-execution) and is
   tested (`tests/test_video_downloader_interactive_tool.py`). This
   remains a footgun for any future tool author who doesn't know the
   convention - flagged in the audit, not fixed structurally.

6. **A caller-side timeout does not free a stuck worker thread.**
   Python threads can't be forcibly killed. `WorkflowStep`'s existing
   timeout (`ThreadPoolExecutor` + `future.result(timeout=...)`) lets
   the *caller* stop waiting, but its own `with` block still blocks on
   `executor.shutdown(wait=True)`, so the orphaned task keeps running
   regardless. The only thing that actually frees the thread for a
   browser-related hang is killing the real OS process - which is what
   `BrowserManager`'s new watchdog does. This does NOT generalize to a
   "tool execution timeout" for non-browser hangs - that's a separate,
   still-open design question.

# What's genuinely undecided right now

Two items, in the person's own stated priority when last asked:

1. **General tool-execution timeout.** Separate from the
   `BrowserManager` watchdog (which only helps once a tool actually
   calls `acquire(timeout=...)` - nothing does yet). Whether/how to
   generalize this is unresolved.
2. **No authentication on the REST API at all.** Low risk while
   local-only; a real risk the moment this is exposed beyond one
   machine. Combined with CORS being wide open
  (`allow_origins=["*"]` + `allow_credentials=True]` in `main.py`),
  this is worth raising proactively if the person seems to be moving
  toward deploying this anywhere beyond their own machine.

Don't decide either of these unilaterally - both were raised and
explicitly left for the person to weigh in on.

# Full audit findings (2026-08-02) - most still open

A full platform audit was done this session (everything outside
video_downloader/CAPTCHA specifics). Six "minor" items were fixed as a
batch (`.gitignore`, `Config` validation, two doc-drift fixes, an
unused import, an API param-collision guard). Everything else found is
**recorded but not fixed** - see `docs/ARCHITECTURE_CHANGELOG.md`'s
"Full Platform Audit" and "Known Technical Debt" sections for the
complete list with full detail. Headline items, so you don't have to
go dig immediately:

- `Config.get()` doesn't type-coerce env var overrides - crashes for
  ints, silently wrong for bools. Confirmed by reproduction.
- `tool.finished` event never fires for background jobs (only sync).
- `context.report_progress()` is disconnected from `job.progress` -
  `GET /jobs/{id}` always shows 0% until completion regardless of what
  a tool reports.
- `POST /tools/{name}/run` can misclassify a tool's own internal
  `KeyError` as "Unknown tool" (404).
- `main.py`'s comment above `include_router(video_downloader_router)`
  is stale (claims it still bypasses the kernel - no longer true).
- `JobManager`/`Scheduler` never clean up old entries (unbounded
  growth). `JobManager.shutdown()` can hang forever on one stuck job.
- `Scheduler` is fully built and tested but has zero REST/CLI surface.
- `GET /api/v1/tools` doesn't expose a tool's `capabilities`.
- `EventBus`/`ServiceContainer` have no locking; `EventBus.emit()`
  doesn't isolate listener failures.
- `PermissionManager` only really enforces the `browser` capability.

None of these are urgent/breaking today. They're recorded so nothing
gets lost, not because they're blocking.

# Established conventions (keep following these)

- **Docs get updated at every milestone** - this was an explicit
  standing instruction from the very first message of the original
  session. `docs/STATUS.md` (checklist), `docs/ARCHITECTURE_CHANGELOG.md`
  (detailed append-only log), `CHANGELOG.md` (root, higher-level),
  `README.md` (roadmap summary) - update all four together.
- **Discuss complex/architectural changes before writing code.** State
  the plan, flag genuine forks explicitly (don't silently pick), then
  implement. This has been the pattern for every non-trivial piece of
  work this session.
- **Verify claims concretely, don't assume from memory** - e.g. this
  session installed the real `seleniumbase` package specifically to
  confirm API details (`sb.driver`, `activate_cdp_mode()`'s role,
  `browser_pid` attribute) before writing code against them, rather
  than trusting recollection. Several real bugs were caught this way
  (e.g. `main.py` having no module-level `app` despite the Dockerfile
  already expecting `uvicorn main:app`).
- **Tests use manual save/restore patching** (try/finally around
  swapping a module attribute), not `unittest.mock`/`monkeypatch`
  fixtures - consistent across the whole test suite. Fakes/stubs are
  plain classes.
- **Prefer real verification over mocks where practical** - e.g. the
  watchdog tests spawn real `sleep 100` subprocesses and confirm the
  manager actually kills them, rather than mocking `os.kill`.
- **Flag sandbox limitations honestly instead of implying more
  confidence than earned.** This environment has no Chrome binary, and
  network egress is restricted to an allowlist that doesn't include
  chromedriver's download host or `dl.google.com` - real browser
  launches and the Dockerfile's Chrome install step are NOT verified
  end-to-end. Say so plainly when relevant, don't gloss over it.

## Git workflow specifics

- The person provided a GitHub PAT for pushing. Pattern: `git remote
  set-url origin https://<token>@github.com/albertsalendah/multi-tool-app.git`,
  push, then immediately `git remote set-url origin
  https://github.com/albertsalendah/multi-tool-app.git` to strip the
  token back out of the local git config.
- **Never put backticks in a commit message passed via `-m "..."` in
  double quotes** - bash interprets `` `text` `` as command
  substitution and will actually execute it, silently corrupting the
  message (this happened twice earlier in the session: once
  accidentally running `uvicorn main:app`, corrupting the message
  around it). Always write commit messages to a heredoc file first
  (`cat > /tmp/msg.txt << 'MSGEOF' ... MSGEOF`) and commit with
  `git commit -F /tmp/msg.txt`.
- `logs/app.log` gets created by running the Logger/Kernel locally.
  It's now in `.gitignore` (`logs/*.log`, fixed this session) - no
  longer need to manually `rm` it before every commit, but it doesn't
  hurt to check `git status` before committing regardless.
- Run tests, then a real integration smoke test (spin up `main.py`'s
  actual app, hit it with `curl` or a real HTTP client over an actual
  socket) before committing anything non-trivial - this has caught
  real bugs that unit tests alone missed (e.g. the `STATIC_DIR` path
  bug that made the video downloader page 500 on every request).

# Sandbox environment notes

- No Chrome/Chromium binary, no Docker daemon.
- Network egress restricted to an allowlist (`pypi.org`, `github.com`,
  etc.) - does NOT include chromedriver's download host or
  `dl.google.com`. A real `seleniumbase` `acquire()` call reaches
  genuine driver-download code but its outcome is inconsistent (fast
  403 in one run, 30+ second hang in another) - environment-specific,
  not a code defect, but not something provable here either.
- `pip install` sometimes needs `--break-system-packages`, and
  occasionally `--ignore-installed pip` (a Debian-packaged `pip`
  conflicts with letting pip upgrade itself as a transitive dependency
  - hit this installing `seleniumbase`).
- `seleniumbase`, `yt-dlp`, `httpx`, `fastapi`, `uvicorn`, `pydantic`
  are all installed in this sandbox's Python environment already (not
  via a persistent venv - if a fresh sandbox/session starts without
  these, reinstall as needed; they're all in `requirements.txt` /
  `pyproject.toml` already, just not necessarily present in a brand
  new container).
