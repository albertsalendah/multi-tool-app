CAPTCHA Domain-Lock Spike

Does a site key extracted from a real target site still render when embedded on a different domain (yours)? This is the one question that decides whether the "native widget" approach is viable at all.

How to get a real site key

  1. Find a real site that shows one of these three CAPTCHA types (a login page, a signup form, a "protected by Cloudflare" page - anything that trips a challenge). Use an ORDINARY site, not a CAPTCHA-solving service's own demo page - those are deliberately left embeddable and won't tell us anything about a typical site's real configuration.
  2. Open browser DevTools -> Network tab, reload the page, filter for recaptcha / hcaptcha / turnstile.
  3. Find the iframe request URL. The site key is the value after k= (reCAPTCHA) or sitekey= (hCaptcha/Turnstile) in that URL - just that value, not the whole URL. For hCaptcha specifically: double check you're not grabbing the hash that appears in the URL PATH (/captcha/v1/<hash>/static/hcaptcha.html) - that's hCaptcha's own client release version, not the site key, even though both can look like similar hex strings.
  4. Paste it into the matching box below and click Render.

Important: serve this over HTTP, not file://

  1. Save this file, then from its folder run: python3 -m http.server 8000
  2. Open http://localhost:8000/captcha-domain-lock-spike.html - some vendor SDKs behave differently (or reject outright) on a file:// origin, which would give you a false negative.

What to look for

A domain-lock rejection usually renders inside the widget box itself as an error (e.g. reCAPTCHA shows "ERROR for site owner: Invalid domain for site key" or "Localhost is not in the list of supported domains for this site key" right where the checkbox should be) rather than a JS console error - so watch the box above each status line, not just the status line itself. If the real checkbox/challenge renders and is interactive, that vendor is not locking this particular site key to its original domain.

IMPORTANT: test each vendor in isolation (reload the page fresh between vendors, don't render two vendors on the same page load). hCaptcha ships a reCAPTCHA-compatibility shim (recaptchacompat) that hijacks window.grecaptcha once hCaptcha's own SDK has loaded on the page - this caused a real false result during testing (a reCAPTCHA key got silently routed to hCaptcha's servers instead of Google's). Testing one vendor per page load avoids this entirely.
