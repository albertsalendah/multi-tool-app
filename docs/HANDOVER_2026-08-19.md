# Part 2: CAPTCHA / video_downloader - active design exploration

This is genuinely mid-thought, not a settled design. The person wants
to eventually generalize this beyond `video_downloader` too ("when a
tool require user to put a link" was the original framing) - keep
that in mind rather than over-fitting the design to this one tool.

## The core idea (person's own framing)
Make CAPTCHA handling a pre-flight *gate* any link-based tool goes
through, not something baked into one tool's pipeline the way
`video_downloader_interactive/pipeline.py` does today. Concretely: a
link is checked for a CAPTCHA before any tool touches it; if clean, it
passes straight through; if a CAPTCHA is found, try to solve it
automatically, and if that's not possible, show it to the person and
wait (with a real, configurable timeout - "not sure if 5 minutes is
enough" was the person's own words) before cancelling the job
outright if unsolved. The tool itself should never see a
CAPTCHA-gated link.

This is not a new idea invented this session - `docs/implementation/
CAPTCHA_MANAGER.md` already describes the CAPTCHA Manager as
"tool-agnostic" and "used by Browser Manager and Tools" (plural). The
current code doesn't match that description yet - `CaptchaManager` is
only ever instantiated inside `video_downloader_interactive`'s own
pipeline. The gate idea is really "make the code match what the docs
already said."

## Key decisions made so far
1. **Cheap-first CAPTCHA detection**: check via a plain HTTP request
   first (no browser cost), fall back to a real browser + CDP-level
   check (`CaptchaManager.check()`, what already exists) only if the
   cheap check is inconclusive. Not yet implemented - `CaptchaDetector`
   currently only runs against a live DOM via `sb.cdp.*`/
   `sb.execute_script()`; adapting its text/selector fingerprinting to
   work against a raw HTTP response body hasn't been designed yet.
2. **Deployment target is eventually-remote**, not just local
   single-user. This materially changes the "how do we show the
   CAPTCHA to the person" question - confirmed explicitly by the
   person, not assumed.
3. **CAPTCHA-solving UX approach: native widget embedding ("Option
   A"), not a third-party paid solving API ("Option B")** - Option B
   explicitly rejected ("this app wont give me money so no way"). The
   idea: extract the real vendor site key from the target page, render
   the *actual* vendor widget (reCAPTCHA/hCaptcha/Turnstile's own JS
   SDK) directly in the app's own frontend, let the person solve it
   natively (no relay of any kind for that interaction), then inject
   the resulting solved token into the real automated browser session.
   This exists specifically because relaying screenshots/video of a
   remote browser for the person to solve a puzzle captcha through was
   already tried and "doesn't feel natural."
4. **The one real risk for Option A is domain-locking**: a site owner
   can restrict their vendor site key to specific registered domains.
   If a target site's key is locked to its own domain, rendering that
   same key on this app's frontend may simply get rejected - this is
   not fixable on this app's end, it's the target site's own
   configuration. This needed real-world verification before investing
   further, which is what Spike 1 below is for.
5. Scope note on CAPTCHA types: reCAPTCHA/hCaptcha/Turnstile are true
   site-key+widget systems, Option A applies. GeeTest/Arkose are
   widget-based but with more involved multi-step protocols (treat as
   maybe-later). Imperva/Datadome/PerimeterX/AWS WAF are
   behavioral/fingerprint blocking systems with no user-facing "solve
   this" step in the same sense - Option A doesn't apply to them at
   all.

## Spike 1: domain-lock testing
File: `docs/spikes/captcha-domain-lock-spike.html` (standalone, run via
`python3 -m http.server` locally - must be served over HTTP, not
`file://`, or some vendor SDKs behave differently). Renders a real
vendor widget (reCAPTCHA v2 / hCaptcha / Turnstile, each in its own
isolated test to avoid cross-vendor contamination - see bug note
below) given a site key pasted in, so the person can tell immediately
whether a real extracted key still works when embedded on `localhost`.

**Findings so far:**
- **reCAPTCHA v2: CONFIRMED domain-locked.** Real site key from
  Facebook, real unambiguous Google-branded rejection: "Localhost is
  not in the list of supported domains for this site key." Trustworthy
  result - correct branding, correct key length (40 chars), no
  contamination.
- **hCaptcha: inconclusive, needs a clean re-test.** Two separate
  issues surfaced, both now understood:
  - *A real bug in the spike tool itself* (now fixed): hCaptcha's SDK
    ships a `recaptchacompat` mode that hijacks `window.grecaptcha`
    once hCaptcha's own script loads - this silently routed a
    reCAPTCHA test's key to hCaptcha's servers instead of Google's,
    on an earlier version of the test page that put multiple vendors
    on one page load. Fixed by testing each vendor in isolation
    (documented directly in the spike file's own notes section now).
  - *A likely key-extraction mistake*: the hCaptcha key tested
    (`1dab630d2576352c6ab33820f3c19d7400cd0955`, from Discord) is
    identical to the hash that appears in the iframe URL's *path*
    segment (`/captcha/v1/<hash>/static/hcaptcha.html`), which is
    normally hCaptcha's own client release version - not the site key,
    even though both look like similar hex strings. Needs re-extraction,
    double-checking it's specifically the `sitekey=` query parameter
    value.
  - Suggested next step: test hCaptcha's official always-passing
    public test key first as a control (confirms the harness itself
    works before trusting any real-site result), then re-extract a
    real key carefully and re-test.
- **Turnstile: not yet tested.** The person has seen it in normal
  browsing (a real, ordinary site's genuine configuration - a good
  test case, better than hunting for an unfamiliar site) but hadn't
  extracted a key yet when this session ended.

**Also worth knowing**: 2captcha.com's own demo pages (e.g.
`2captcha.com/demo/recaptcha-v2`) are *not* useful test cases - they're
built by a CAPTCHA-solving service specifically to be embeddable from
anywhere, so their keys are likely deliberately left unlocked and
won't tell us anything about how an ordinary site is configured. BU's
(`bu.edu`) tech docs confirm reCAPTCHA is on *every* Gravity
Forms-powered contact page across that domain, if a guaranteed-real
reCAPTCHA example is needed again.

## Spike 2: CDP native screencast (viewing side only)
File: `docs/spikes/captcha_screencast_test.py` (needs
`docs/spikes/style.css` - a copy of the real `static/style.css` - in
the same folder to run). Tests whether Chrome DevTools Protocol's
native frame-push screencast (`Page.startScreencast`, not manual
screenshot polling) looks/feels natural for showing a live remote
browser session to the person.

**Every CDP-level API this script uses was confirmed against the real
installed `seleniumbase`/`mycdp` packages before writing it** -
`mycdp.page.start_screencast`/`screencast_frame_ack`/`stop_screencast`,
the `ScreencastFrame` event's `.data`/`.session_id` fields,
`sb.cdp.page.send()` as the sanctioned way to issue custom CDP
commands (its own docstring says so), `sb.cdp.add_handler()` accepting
either a sync or async callback, `sb.activate_cdp_mode(url)` accepting
a URL directly. None of this was assumed from memory - there is no
dedicated high-level "screencast" method in SeleniumBase itself, this
calls CDP's raw `Page` domain directly through `sb.cdp.page.send()`.

**Result: confirmed to work well** ("it works great" - person's own
words after the first version). Relays frames via a simple MJPEG
multipart HTTP stream (an `<img src="...">` pointing at a
`multipart/x-mixed-replace` endpoint) to a plain browser tab - no
custom JS frame-drawing loop needed.

**v2 wraps this in a mock of the real app UI**, specifically to let
the person judge how this would actually surface before any of it
touches the real backend: the script now serves an unmodified copy of
`static/video_downloader.html`'s real markup, plus one clearly-labeled
test-only button ("Simulate: CAPTCHA required") that reveals a modal
overlay with the live stream inside it. The modal reuses
`static/style.css`'s `.modal-overlay`/`.canvas-wrapper`/
`.canvas-loader` classes - **these already existed in the real CSS,
completely unused by any real HTML/JS in the app**, discovered while
investigating this. Interesting confirmation: those classes were built
around a `<canvas>` element originally, but an `<img>` (needed for the
MJPEG approach that actually worked) slots into the same
`#stream-canvas` styling identically, since `object-fit: contain`
applies to both - no CSS changes were needed.

**Still only tests viewing** - there is no click-forwarding into the
real browser session anywhere in this spike. That's a deliberately
separate, not-yet-started piece.

## Open question for the next session
**How Spike 2 (screencast/modal) actually relates to the Option A
(native widget embedding) direction was never fully resolved in this
session.** Two different things may be getting explored in parallel
without a settled relationship yet:
- If Option A works for a given real site (key isn't domain-locked),
  the person solves the *real* vendor widget natively in the frontend
  - no relay, no screencast, no modal needed for that interaction at
  all.
- The screencast/modal mechanism would matter for cases Option A can't
  cover - a domain-locked key, a non-widget CAPTCHA type, or just
  general "show what the automated browser is doing" visibility
  independent of CAPTCHA-solving specifically.

Worth explicitly clarifying next: is the screencast/modal work meant
as (a) the fallback for when Option A doesn't apply, (b) a
general-purpose "show the browser" mechanism useful beyond CAPTCHA
too, or (c) something the person wants regardless of how the
domain-lock findings turn out? This wasn't asked directly before the
session ended.

# Established conventions (keep following these)

- **Docs get updated at every milestone** - standing instruction since
  the first session. `docs/STATUS.md`, `docs/ARCHITECTURE_CHANGELOG.md`,
  `CHANGELOG.md`, `README.md` for platform work; this handover doc
  pattern for design exploration and session continuity.
- **Discuss complex/architectural changes before writing code.** This
  was followed strictly all session - every non-trivial fix was
  proposed, tradeoffs laid out honestly (including pushing back on the
  person's own framing where warranted, e.g. PermissionManager
  "real enforcement"), and confirmed before implementation.
- **Verify claims concretely, don't assume from memory** - the
  screencast spike's entire CDP API surface was checked against the
  real installed library source before use, exactly this project's
  established pattern (see `docs/HANDOVER_2026-08-02.md` for the
  original instance of this convention).
- **Tests use manual save/restore patching**, not `unittest.mock`/
  `monkeypatch` fixtures. Fakes/stubs are plain classes.
- **Real verification over mocks where practical** - every fix this
  session was confirmed with a real `uvicorn` boot + `curl` (and once,
  the actual installed `multitool` CLI) in addition to the unit test
  suite, not unit tests alone.
- **A GitHub PAT was used for pushing this session, provided directly
  in chat.** Standing advice: treat any token pasted into a
  conversation as compromised and rotate it, regardless of whether
  anything has gone wrong - this was raised multiple times. Pattern
  when pushing: set it into the remote URL, push, then immediately
  strip it back out (`git remote set-url origin
  https://github.com/albertsalendah/multi-tool-app.git`) so it's never
  left sitting in local git config.
- **Never put backticks in a commit message passed via `-m "..."` in
  double quotes** - write to a heredoc file first
  (`cat > /tmp/msg.txt << 'MSGEOF' ... MSGEOF`), commit with
  `git commit -F /tmp/msg.txt`.
- **Sandbox note for whoever picks this up next**: the code-execution
  sandbox has no real display/Chrome/network access to arbitrary
  sites (network egress is allowlisted to package registries and
  GitHub, nothing else) - anything requiring a real browser or fetching
  an arbitrary external page has to run on the person's own machine.
  This is why both spikes in Part 2 are standalone scripts handed to
  the person to run themselves, not things verified end-to-end from
  within a chat session.
