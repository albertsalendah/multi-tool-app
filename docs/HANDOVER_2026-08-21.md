# The screencast + click-forwarding spike: now confirmed working

File: `docs/spikes/captcha_screencast_test.py` (needs
`docs/spikes/style.css` in the same folder to run - copy of the real
`static/style.css`). Now on v3. Real reCAPTCHA image-selection
challenges (not just the checkbox) were solved successfully from
desktop Firefox, desktop Chrome, Android Chrome, and 1DM+, across two
physical machines plus a phone over LAN - not a cherry-picked result,
this was the outcome of deliberately testing across every combination
available.

## What changed since 2026-08-19 (v1/v2 -> v3)

**1. MJPEG push transport confirmed broken in Chrome/Chromium,
replaced with plain polling.** v2 relayed frames via a single
long-lived `multipart/x-mixed-replace` HTTP connection per viewer
(classic "MJPEG stream"). Real cross-device testing found it worked in
desktop Firefox but silently failed in Chrome (desktop and Android)
and 1DM+ (Chromium-based). This was isolated properly, not guessed at:
added server-side connect/write/disconnect logging, which showed
*identical* bytes written via *identical* server-side behavior to both
a working (Firefox) and a broken (Chrome) client - proving the break
was entirely client-side, not a server or CDP-capture bug. Chrome-
family browsers connected, received a partial write, then silently
went quiet with no error the server ever saw. v3 drops MJPEG entirely
in favor of the client polling a plain `GET /frame` endpoint
(single JPEG per request) on a `setInterval` with a cache-busting query
param - works identically everywhere since it's nothing but ordinary
repeated HTTP GETs, no reliance on any browser's multipart handling.

**2. Click-forwarding added, and confirmed correct, not just
plausible.** Client computes a click's position as a fraction of the
actual rendered image content (accounting for `object-fit: contain`
letterboxing, so edge clicks near the letterbox bars aren't
misattributed to the image), posts `{frac_x, frac_y}` to `POST
/click`. Server parses the current frame's real pixel dimensions
directly from the JPEG's own SOF marker (a ~20-line stdlib parser -
avoided adding Pillow as a new dependency just for this), scales by
the screencast frame's own `ScreencastFrameMetadata`
(`device_width`/`device_height`/`offset_top`/`page_scale_factor` -
field names confirmed against the real installed `mycdp` package) into
real CSS-pixel viewport coordinates, and dispatches
`mousePressed`/`mouseReleased` via CDP's `Input.dispatchMouseEvent`
(signature and the `MouseButton` enum both confirmed against the real
installed package before use, same as every other CDP call in this
file). The coordinate formula was built from CDP's documented field
semantics with no worked reference example found to cross-check
against, and was shipped the first time explicitly flagged as
unverified. Solving real multi-tile image challenges across four
browser/device combinations afterward is good evidence the math is
actually right, not just reasonable-looking.

**3. `headless=True` retested clean - correcting an earlier
overconfident claim.** Worth reading carefully, since it's a real
epistemic correction, not just a status update: earlier testing (under
the old v2 MJPEG transport) showed the frame counter climbing but the
displayed image staying blank under `headless=True`, and this was
attributed in conversation to "a known Chromium headless-screencast
rendering limitation" - stated with more confidence than was actually
earned. That claim was never checked against real captured frame bytes
from a headless run specifically; only `headless=False` frames were
ever byte-verified (via debug `frame_N.jpg`/`seed_frame.jpg` dumps
added specifically to settle where in the pipeline a different bug
was). Retested under v3's polling architecture with `headless=True`:
works cleanly, no blank frames. Most likely the original observation
was actually the same Chrome/MJPEG bug from point 1, coincidentally
present in that specific test too, not a genuine headless-capture
limitation.

**Why this matters beyond the spike itself**: `tools/
video_downloader_interactive/tool.py` hardcodes `headless=False`
specifically so a human can *see* the real browser window to solve a
manual CAPTCHA. If a human can instead solve it remotely through this
screencast+click-forwarding mechanism, that requirement may no longer
apply - and headless is exactly what's wanted for the actual
eventually-remote deployment target, where there's no display to hand
a real window to at all. **Only lightly retested so far** (a handful
of manual runs, not a stress test) - worth a couple more full solves
under `headless=True` before leaning on this for a real design
decision, but it's a promising, unplanned finding.

**4. Sizing/blur fixed for the spike, explicitly NOT for production.**
The captured frame is the *whole page*, so a small widget on a large
page (like the reCAPTCHA demo form) renders tiny, and at fixed JPEG
quality, blurrier than it needs to be. Fixed for testing purposes by
shrinking the real browser window (`Page.setWindowSize` via CDP, right
after `activate_cdp_mode`) so the page - and the widget within it -
fills proportionally more of the frame, plus a quality bump (70 -> 85)
now that there's headroom. **This is explicitly flagged in the script
itself as not viable in production**:
`video_downloader_interactive` runs against arbitrary third-party
sites, and forcing a small viewport globally risks tripping a site's
own mobile/responsive layout, changing where or whether the CAPTCHA
even renders in the first place. The real fix, not built yet, is
cropping the encoded frame to the actual CAPTCHA element's on-page
bounding box - findable via `libraries/captcha_manager`'s existing
detector/selector logic (`CaptchaDetector.scan_iframes()` already
locates the relevant iframe), rather than shrinking the window
globally.

**5. Minor: fixed a Ctrl+C hang** during manual testing - a second,
impatient interrupt could land inside SeleniumBase's own `--uc`
teardown/reconnect logic and hang rather than exit. Worked around with
`os._exit(0)` on the first interrupt instead of a bare `return` (which
still triggers `with SB(...)`'s normal `__exit__`/teardown path - the
thing that was actually hanging). Test-script-only concern - production
never has a Ctrl+C loop; browser lifecycle goes through
`BrowserManager.release()` via the normal job lifecycle instead.

## Still open, unresolved

These were open before this session and remain open - this session
was about proving the *mechanism* works, not deciding where it fits:

1. **The crop-to-actual-widget-location design** (point 4 above) -
   needed before this could work against real, arbitrary third-party
   sites rather than a controlled demo page.
2. **How this whole mechanism relates to the Option A (native
   widget embedding) direction** - the exact same open question from
   the 2026-08-19 handover, still not asked/answered: is the
   screencast/modal work meant as (a) the fallback for when a site's
   key is domain-locked (Option A doesn't apply), (b) a general-purpose
   "show what the automated browser is doing" feature useful beyond
   CAPTCHA-solving, or (c) something wanted regardless of how the
   domain-lock spike (Spike 1, separately) turns out? This session's
   results make the screencast path look considerably more viable than
   it did on 2026-08-19, which makes this question more urgent to
   settle, not less.
3. **Spike 1 (domain-lock testing,
   `docs/spikes/captcha-domain-lock-spike.html`) untouched this
   session** - still exactly where 2026-08-19 left it: reCAPTCHA v2
   confirmed domain-locked, hCaptcha needs a clean re-test (wrong key
   segment extracted last time), Turnstile not yet started. See the
   2026-08-19 handover for full detail - nothing to add here.
